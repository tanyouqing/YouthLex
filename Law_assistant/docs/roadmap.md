# 青律 Legal Triage Agent Roadmap

本文用于梳理项目从“当前可运行原型”推进到“可正式交付 Agent”的工作路线。内容以当前仓库实现状态为基线，强调可执行、可验收、可拆分开发。

## 1. 当前项目状态

截至目前，项目已经具备以下基础能力：

- 已完成 `FastAPI + LangGraph + MiniMax` 后端骨架
- 已完成 5 阶段图流程：
  - 情绪安抚与共情
  - 法条亮剑与定性
  - 证据链完善与填槽
  - 维权 SOP 指导
  - 核心交付物生成
- 已完成 MiniMax 实际调用
- 已接入官方得理检索：
  - `legal_grounding` 节点接法规检索
  - `deliverables` 节点接类案检索
- 已完成基础测试，当前后端可运行、可返回结构化结果

当前版本的定位仍然是“可运行原型”，还不属于“正式交付版本”。

## 2. 正式交付目标

正式交付版本应满足以下目标：

- 用户首句可以被正确识别并路由到对应维权场景
- 支持多轮补充事实和证据，而不是单轮静态生成
- 输出内容稳定包含：
  - 情绪安抚
  - 初步法律定性
  - 缺失证据提醒
  - 分阶段维权 SOP
  - 可直接复制的催告函
  - 真实相似案例摘要
- 对检索失败、模型失败、用户信息不足等情况具备明确降级策略
- 文档、测试、部署说明齐全，能支撑比赛演示或正式验收

## 3. Roadmap 总览

建议将后续工作分成 6 个阶段推进：

1. 场景识别与检索命中率提升
2. 证据槽位抽取与多轮状态管理
3. 核心业务输出质量提升
4. 工程稳定性与异常治理
5. 前端对接与演示能力补齐
6. 交付收尾与文档完善

## 4. 分阶段工作步骤

### 阶段一：场景识别与检索命中率提升

目标：让系统更准确理解用户问题，并把检索做得更“像法律产品”，而不是直接拿原话搜索。

工作项：

- 实现 5+1 场景自动路由
  - 支持从用户首句自动识别：
    - `housing`
    - `labor`
    - `consumer`
    - `debt`
    - `ip_reputation`
    - `other`
  - 保留前端手动指定 `scenario` 的能力
- 新增检索查询改写能力
  - 为法规检索生成更适合 `queryListLaw` 的自然语言问题
  - 为类案检索生成更适合 `queryListCase` 的关键词或长文本
  - 针对不同场景设计不同改写模板
- 优化得理接口调用策略
  - 明确什么时候用 `keywords`
  - 明确什么时候用 `longText`
  - 统一法规和类案的默认 `pageSize`

阶段验收标准：

- 给定典型输入时，场景分类基本正确
- 检索命中率和相关性优于“直接用原话检索”
- 检索查询可在日志中追踪，便于调试

### 阶段二：证据槽位抽取与多轮状态管理

目标：把项目从“单轮回答器”升级为“引导式维权 Agent”。

工作项：

- 完成“纠纷六要素”正式抽取
  - 相对方信息
  - 时间地点
  - 标的金额
  - 合同约定
  - 违约事实
  - 现有证据
- 新增槽位状态管理
  - 区分已确认、缺失、待确认
  - 避免同一个问题反复询问
- 实现多轮对话推进
  - 每轮补充信息后更新图状态
  - 自动判断当前应该继续追问、输出 SOP，还是生成交付物
- 增加会话级上下文存储方案
  - 先支持内存态会话
  - 后续再考虑数据库持久化

阶段验收标准：

- 用户连续补充 2 到 4 轮信息后，系统能持续更新证据链
- 缺失槽位提示具有针对性
- 不会因为单轮输入不足而直接生成“假完整”的维权方案

### 阶段三：核心业务输出质量提升

目标：让输出更像一个正式法律辅助产品，而不是“通用聊天回复”。

工作项：

- 提升法律定性节点质量
  - 绑定检索到的法规结果做定性
  - 输出“事实判断 + 法律依据 + 风险提示”
  - 避免无依据地写具体法条编号
- 提升维权 SOP 节点质量
  - 按场景做分支模板
  - 输出按时间顺序的步骤
  - 明确平台入口、部门类型、建议动作
- 提升催告函生成质量
  - 按场景建立模板
  - 自动代入用户已知事实与诉求
  - 输出更适合直接复制发送的 Markdown
- 提升案例展示质量
  - 对检索结果做摘要与去噪
  - 固定展示格式：
    - 案情摘要
    - 判决结果
    - 维权启示
  - 只展示最相关的 1 到 2 条

阶段验收标准：

- 输出内容结构稳定
- 催告函具备实际发送价值
- 相似案例可读、可信、不过度冗长
- 不同场景下的回答风格和重点有明显差异

### 阶段四：工程稳定性与异常治理

目标：把当前原型升级为可稳定演示、可持续维护的后端服务。

工作项：

- 完善错误分类与降级逻辑
  - MiniMax 请求失败
  - 得理检索失败
  - 检索为空
  - 用户输入过少
  - 模型返回结构异常
- 增加日志与可观测性
  - 记录场景路由结果
  - 记录检索 query
  - 记录各节点耗时
  - 记录降级触发原因
- 完善超时与重试策略
  - 模型调用超时
  - 检索接口超时
  - 是否需要指数退避
- 补齐测试矩阵
  - 单元测试
  - 图节点测试
  - API 集成测试
  - mock 检索 / mock LLM 测试
  - 可选真实联调测试

阶段验收标准：

- 核心接口在检索失败或模型失败时仍返回 200 和可用结果
- 核心场景具备稳定测试覆盖
- 日志足够支持排错和比赛演示排查

### 阶段五：前端对接与演示能力补齐

目标：让 Agent 更适合接入页面或演示系统，而不是只在接口层可用。

工作项：

- 固定前后端接口契约
  - 对话区返回字段
  - 侧边栏返回字段
  - 每轮更新的最小数据结构
- 补充更明确的响应结构说明
  - 哪些字段是稳定字段
  - 哪些字段可能为空
  - 降级场景下字段表现如何
- 评估是否支持流式输出
  - 共情与定性先返回
  - 交付物稍后补齐
- 准备演示数据与示例场景
  - 房东不退押金
  - 兼职拖欠工资
  - 借钱不还
  - 教培退费
  - 网暴 / 名誉侵权

阶段验收标准：

- 前端可以稳定消费现有接口
- 核心演示场景可一键复现
- 输出结构清晰，适合比赛展示

### 阶段六：交付收尾与文档完善

目标：补齐正式交付所需的文档、说明和操作手册。

工作项：

- 更新主 README
  - 当前能力
  - 运行方式
  - 环境变量说明
  - 接口说明
  - 已知限制
- 补充系统设计文档
  - 图节点职责
  - 检索链路
  - 模型调用链路
  - 降级机制
- 补充部署文档
  - 本地启动
  - 测试命令
  - 环境变量配置
- 补充演示说明文档
  - 推荐演示流程
  - 推荐样例输入
  - 常见异常与处理方式

阶段验收标准：

- 新同学可按文档完成本地启动和测试
- 评审可快速理解系统结构和能力边界
- 文档内容与代码实现保持一致

## 5. 推荐开发顺序

建议按下面顺序推进，避免后面返工：

1. 场景自动路由
2. 检索 query 改写
3. 证据槽位抽取
4. 多轮状态管理
5. SOP 场景化增强
6. 催告函模板化增强
7. 类案展示优化
8. 异常治理与日志
9. 完整测试
10. 文档和演示整理

## 6. 可正式交付的验收标准

当项目满足以下条件时，可以认为已接近“正式交付”：

- 支持 5+1 场景识别
- 支持至少 2 到 4 轮证据补充
- 能稳定输出法律定性、SOP、催告函、相似案例
- 检索失败时具备明确降级结果
- 核心场景测试通过
- README、路线图、接口说明、部署说明完整

## 7. 当前建议的近期优先级

如果只看接下来 1 到 2 个开发迭代，优先做这四件事：

1. 实现场景自动路由
2. 实现检索 query 改写
3. 实现证据槽位自动抽取
4. 实现多轮会话状态更新

这四项完成后，项目会从“有图流程的原型”明显提升到“真正可演示的 Agent”。
